# Задание 6 — Реализовать функциональность создания файлового образа диска и сохранения в него зашифрованных файлов

Консольная утилита для создания файлового образа диска и сохранения в него зашифрованных файлов с использованием алгоритма поточного шифрования RC4.

## Возможности

- Создание нового образа и добавление файлов (с автоматическим созданием образа при первом `-add`)
- Добавление файлов и директорий (рекурсивный обход поддиректорий любой глубины)
- Просмотр перечня файлов в образе с указанием размера
- Извлечение и расшифровка конкретного файла
- Параллельное шифрование и запись до 5 потоков
- Совместимость с реализациями других студентов (фиксированный little-endian бинарный формат образа)
- Поддержка флагов с одним тире (`-key`) и двумя (`--key`)
- Поддержка позиционных аргументов для `-get` без флага `-out`

## Сборка

```bash
make
```

Результат: `librc4.so` (разделяемая библиотека шифрования) и `secure_copy` (исполняемый файл).

Требования: `gcc`, `g++`, Linux x86/x64.

## Использование

### Добавление файлов и директорий в образ

```bash
./secure_copy -add -key "secret" -image disk.img file1.txt file2.txt in/
```

Если образ не существует, он создаётся автоматически. При указании директории все файлы в ней и её поддиректориях добавляются рекурсивно. Имена файлов внутри директории хранятся как относительные пути (например, `sub/2.txt`). Для одиночных файлов используется базовое имя (например, `file1.txt`).

### Просмотр перечня файлов

```bash
./secure_copy -list -image disk.img
```

Выводится список файлов, упорядоченный по имени. Для каждого файла указывается его размер в байтах. При наличии дубликатов (файлов с одинаковым именем) показывается последняя версия.

### Извлечение файла

С флагом `-out`:

```bash
./secure_copy -get -image disk.img -key "secret" -out result.txt /root.txt
```

Без флага `-out` (позиционные аргументы):

```bash
./secure_copy -get -image disk.img -key "secret" result.txt /root.txt
```

Программа ищет в образе файл с указанным именем (последнее вхождение при дубликатах), расшифровывает его и сохраняет в файл результата.

## Формат образа

Образ диска представляет собой последовательность файловых записей без общего заголовка. Новые файлы дописываются в конец файла образа (аппенд).

Структура каждой записи:

| Смещение | Размер (байт) | Тип          | Описание                            |
|----------|----------------|---------------|-------------------------------------|
| 0        | 4              | uint32_t LE   | Размер исходного файла (m)          |
| 4        | 4              | uint32_t LE   | Длина имени файла (n)               |
| 8        | 16             | raw bytes     | Соль (случайная, /dev/urandom)      |
| 24       | n              | UTF-8         | Имя файла (путь внутри директории)  |
| 24 + n   | m              | raw bytes     | Зашифрованное содержимое (RC4)      |

Все числовые поля записываются в формате **little-endian** (LE32) через функции `write_le32()`/`read_le32()`. Это гарантирует совместимость между реализациями разных студентов на любой архитектуре, а не только на x86/x64. Нативный `memcpy(&val, buf, 4)` зависит от порядка байт процессора и непортируем.

## Шифрование RC4

Используется стандартный RC4, состоящий из двух этапов:

1. **KSA (Key-Scheduling Algorithm)** — инициализация S-box на основе ключа шифрования. S-box заполняется значениями от 0 до 255, затем перемешивается с использованием байтов ключа.

2. **PRGA (Pseudo-Random Generation Algorithm)** — генерация псевдослучайной гаммы (keystream) и побайтовое XOR с открытым текстом. Шифрование и расшифрование идентичны (XOR с той же гаммой).

### Формирование ключа

Ключ шифрования для каждого файла формируется как конкатенация мастер-пароля и 16-байтной соли:

```
RC4_key = master_password_bytes || salt_bytes
```

Соль гарантирует уникальность keystream для каждого файла, даже при одинаковом мастер-пароле. Без соли XOR двух шифротекстов файлов с одним ключом дал бы XOR открытых текстов — критическая уязвимость поточного шифра. Соль хранится в открытом виде в заголовке записи.

### Один непрерывный RC4-поток на файл

Для каждого файла RC4 инициализируется один раз (один вызов KSA), после чего генерация гаммы продолжается непрерывно через всё содержимое файла. Файлы читаются и записываются порциями по 4096 байт, но это исключительно механизм ввода-вывода — криптографически это один непрерывный поток. Внутреннее состояние шифра (индексы i и j в S-box) сохраняется между порциями данных.

### Жизненный цикл шифрования

1. `init_file_crypto(salt)` — вызывается один раз. Формирует полный ключ (пароль + соль), выполняет KSA, закрывает страницу S-box через `mprotect(PROT_NONE)`. Возвращает 0 при успехе, -1 при ошибке (mmap/mprotect не удался).

2. `rc4_crypt(src, dst, len)` — вызывается многократно (по одному разу на каждый чанк данных). Открывает страницу S-box, выполняет PRGA, закрывает страницу. **Возвращает 0 при успехе, -1 при ошибке** (S-box не инициализирован, уже уничтожен, или mprotect не сработал). Если функция вернула -1, данные в `dst` не изменялись корректно — операцию следует прервать.

3. `end_file_crypto()` — вызывается один раз после обработки всего файла. Зануляет S-box через `explicit_bzero`, освобождает mmap-страницу. После этого вызова `rc4_crypt()` вернёт -1, предотвращая использование уничтоженного состояния.

## Безопасность ключей

### Мастер-ключ в mmap-странице

Мастер-пароль хранится в отдельной странице памяти, выделенной через `mmap`. Когда ключ не используется, страница закрывается через `mprotect(PROT_NONE)` — любая попытка чтения или записи вызывает SIGSEGV. Установлен обработчик SIGSEGV, который выводит `Unauthorized access to master key` при обращении к странице мастер-ключа.

### Мьютекс key_mutex

Поскольку `mprotect` действует на целую страницу для всех потоков одновременно, используется мьютекс `key_mutex` для синхронизации доступа к мастер-ключу. Без него возможна следующая ситуация: поток A закрыл страницу `PROT_NONE` через `mprotect`, а поток B в этот момент читает ключ — происходит SIGSEGV. Мьютекс гарантирует, что изменение прав доступа и чтение ключа не пересекаются во времени.

**Для S-box мьютекс НЕ нужен** — S-box хранится как `__thread` переменная, каждый поток имеет собственную mmap-страницу. Вызов `mprotect(PROT_NONE)` одним потоком затрагивает только его собственную страницу и не влияет на S-box других потоков.

### S-box в thread-local mmap-странице

S-box RC4 выделен в отдельной `mmap`-странице и хранится как `__thread` переменная. Каждый поток имеет собственную страницу, поэтому потоки не мешают друг другу. Между вызовами `rc4_crypt()` страница защищена через `mprotect(PROT_NONE)` — S-box недоступен вне процедуры шифрования, что соответствует требованию ТЗ: «Внутреннее состояние шифра должно быть недоступно вне процедуры шифрования».

### Проверка mprotect

Все вызовы `mprotect()` проверяются через вспомогательную функцию `mprotect_checked()`. Если `mprotect(PROT_NONE)` не сработает — это критическая ошибка безопасности (S-box остаётся доступным). В таком случае S-box немедленно зануляется через `explicit_bzero`, а функция возвращает ошибку. Аналогично, если `mprotect` не смог открыть страницу для чтения/записи — функция возвращает ошибку, предотвращая работу с повреждённым состоянием шифра.

### mlock — защита от swap

Все mmap-страницы (мастер-ключ и S-box каждого потока) блокируются в оперативной памяти через `mlock`. Это предотвращает выгрузку страниц в файл подкачки, где ключи могли бы быть восстановлены после завершения программы. Если `mlock` не удался (недостаточно прав), выводится предупреждение, но работа продолжается.

### Затирание ключей

После формирования полного ключа и выполнения KSA массив `full_key` на стеке зануляется через `explicit_bzero` — компилятор не может оптимизировать и удалить этот вызов. Локальные переменные с копиями индексов RC4 (`i`, `j`) также зануляются через `explicit_bzero` после сохранения значений в thread-local структуру. Использование `explicit_bzero` надёжнее, чем `volatile`-трюк или обычный `memset`, которые компилятор вправе удалить как мёртвый код.

## Параллелизм

### Предрасчёт смещений + pwrite

До запуска потоков программа вычисляет размер каждой записи и назначает смещение. Файл образа создаётся через `ftruncate` (с проверкой возврата), и каждый поток пишет в свою позицию через `pwrite` — системный вызов, атомарный на уровне ядра. Мьютекс на запись не нужен. Возврат `pwrite` проверяется: если записано меньше байт, чем ожидалось, операция прерывается с ошибкой.

### Очередь задач без мьютекса

Потоки берут задачи из массива через `__atomic_fetch_add(&next_index, 1, __ATOMIC_SEQ_CST)`. Каждый поток получает уникальный индекс без блокировок.

### Количество потоков

Не более 5 потоков (`MAX_WORKERS`). Если файлов меньше 5, запускается по одному потоку на файл.

### Сводка по мьютексам

| Ресурс        | Мьютекс    | Причина                                         |
|---------------|------------|-------------------------------------------------|
| Запись в образ | Не нужен   | Предрасчёт смещений + pwrite                     |
| Очередь задач  | Не нужен   | `__atomic_fetch_add`                             |
| Мастер-ключ    | `key_mutex`| `mprotect(PROT_NONE)` влияет на все потоки        |
| S-box          | Не нужен   | `__thread` — у каждого потока своя страница       |

## Ограничение 4 ГБ

Размер файла хранится в поле `uint32_t` (4 байта по ТЗ). Файл, превышающий лимит, пропускается с выводом ошибки. Обработка остальных файлов продолжается. Образ целиком может превышать 4 ГБ — смещения хранятся в `off_t` (64 бита при `_FILE_OFFSET_BITS=64`).

## Обработка ошибок

- Файл не найден при добавлении — предупреждение, обработка продолжается
- Файл превышает 4 ГБ — ошибка, файл пропускается
- Ошибка выделения памяти — ошибка, операция прерывается с освобождением ресурсов и вызовом `end_file_crypto()`
- Ошибка шифрования (`rc4_crypt` вернул -1) — операция прерывается, S-box уничтожается
- Ошибка записи в образ (`pwrite`) — операция прерывается с диагностикой
- Ошибка выделения места (`ftruncate`) — чистый выход с освобождением ресурсов
- Ошибка записи в выходной файл (`fwrite`) — операция прерывается, файл может быть неполным
- Неверный ключ при расшифровке — на выходе мусор (ожидаемое поведение поточного шифра)
- Повреждённый образ — чтение прерывается, выводятся успешно прочитанные записи
- Некорректная длина имени (`name_len == 0` или `> MAX_NAME_LEN`) — запись пропускается
- Ошибка `mprotect` — критическая ошибка безопасности, S-box зануляется, операция прерывается
- Отсутствие `/dev/urandom` — фатальная ошибка (fallback на `rand()` недопустим)

## Совместимость (по ТЗ: «Образ одного студента должен корректно обрабатываться программой другого»)

Для обеспечения совместимости реализованы следующие меры:

- **Little-endian формат**: все числовые поля образа (размер файла, длина имени) записываются и читаются через `write_le32()`/`read_le32()`, а не через нативный `memcpy`. Это гарантирует одинаковый формат на любой архитектуре.
- **`_FILE_OFFSET_BITS=64`** определён до любых `#include`, что обеспечивает 64-битный `off_t` и корректную работу с образами >2 ГБ даже на 32-битных системах при компиляции без Makefile.
- **Единый формат записи**: `[4B file_size][4B name_len][16B salt][name][encrypted_data]` без дополнительного заголовка образа.
